# AlekS DTS: совместимость и безопасная установка на другие LG

## Подтверждённые профили

| Телевизор / платформа | Изолированная проверка | Подключение в штатный плеер |
| --- | --- | --- |
| LG 65NANO896PC, webOS 6.6, ARMv7, GStreamer 1.16.2 | DTS Core / AC3 PASS | DTS Core 5.1 и регрессия DVB-C подтверждены |
| LG UP75006LF, ARMv7, R278 | DTS Core / AC3 PASS по сообщению владельца | Владелец сообщил, что воспроизведение работает; расширенная регрессия не документирована |
| LG 43NANO85A6A, firmware 43.22.74, kernel aarch64, **media ELF32 ARM**, GStreamer 1.24.10 | DTS 2.0/5.1 + программный AC3 PASS; PREVIEW `verify` PASS; установка/откат PASS, действующие 4/4 SHA256 PASS | **DTS в Lampa работает, но первый запуск после перезагрузки бывает БЕЗ ЗВУКА**; реальная пара «тишина → AC3 → звук DTS» зафиксирована R318. Изолированный DTS-декодер выдаёт ненулевой PCM на этом LG (R320). Штатный LG Media Player, DTS 5.1 eARC и постоянное исправление первого запуска — НЕ ПРОВЕРЕНЫ |
| Любые другие модели, версии ABI или GStreamer | **Не проверено** | Не устанавливать без предварительной диагностики |

Нельзя определять архитектуру медиаплеера только по `uname -m`: на кухонном LG ядро ARM64, а `umediaserver` и GStreamer 32-битные.

**Важно (22.11.2026):** старые записи R307–R317 ниже — исторические результаты, а не последнее состояние кухни. Результат R318 впервые подтвердил холодную тишину DTS при нормальных показателях LS2/ALSA; R320 подтвердил ненулевой PCM только в отдельном декодере. [R318](docs/R318_REAL_KITCHEN_FIRST_SILENT_TO_AUDIBLE_PAIR_20261122.md), [R320](docs/R319_R320_DTS_PCM_AMPLITUDE_ISOLATED_HARDWARE_QA_20261122.md). Для OLED77 B1 проверка установки и eARC 5.1 не подтверждена: [R321](docs/R321_OLED77B1_EARC_INSTALL_TRIAGE_20261122.md).

**R325 (22.11.2026, кухня):** в отдельном GStreamer-процессе установленный R278 успешно декодировал DTS Core после экспериментального сборщика кадров с корректным начальным TIME-сегментом: **8/8 положительных + 4/4 отрицательных PASS**, ноль предупреждений. [Полный отчёт](docs/R325_KITCHEN_DTS_TIME_SEGMENT_NATIVE_20261122.md). Этот модуль **не включён** в штатный плеер, поэтому реальная тишина при первом DTS после перезагрузки пока не устранена.

**R326 (22.11.2026, кухня):** подтверждено, что ALSA PCM6 обслуживается потоком PulseAudio; один короткий замер через `pcm_output.monitor` показал **цифровой ноль**, несмотря на `RUNNING`, отсутствие mute/cork и громкость 100%. Однако владелец **не подтверждал в этот момент запуск DTS**, поэтому результат нельзя считать повторением неисправности. Сохранена безопасная методика измерения RMS без записи звука. [R326](docs/R326_REAL_KITCHEN_PULSEAUDIO_PCM_MONITOR_20261122.md).

## Первый шаг на неизвестной модели

В root SSH устройства (или через `ares-novacom --device <профиль> --run "..."`) запустите **только read-only** диагностику:

```sh
curl -fLsS 'https://raw.githubusercontent.com/aerolit266/AlekS-DTS-webOS/cec9b978e65750a51a12ca21aeaf32adef691581/tools/public-compatibility-check.sh' -o /tmp/aleks-dts-compat.sh &&
printf '%s  %s\n' '70da08090cc9d1c25a9b069c22f072882384234b2e5203d130a7d9b76f664d44' /tmp/aleks-dts-compat.sh | sha256sum -c - &&
sh /tmp/aleks-dts-compat.sh
```

Присылайте в [Issues](https://github.com/aerolit266/AlekS-DTS-webOS/issues) модель, webOS, фактический ELF ABI, GStreamer, статус встроенного AC3 и тестовый результат. Секреты, ключи SSH, содержимое `umediaserver.env` и приватные данные **не публикуйте**.

**R307 (22.11.2026):** оригинальные ARM32-библиотеки релиза R278 и его DTS-клипы проверены по SHA256. Штатная проверка релиза использует сформированные пакеты Matroska. На VPS при извлечении тех же DTS-данных в сырой поток и разбиении на 11/97-байтные блоки наблюдается потеря PCM; Matroska сохраняет полный результат. [R307](tools/audit-r278-release-packet-boundaries-r307.py) PASS. **Бинарники конкретного кухонного LG не сверены; лабораторные результаты не означают исправления тишины DTS.**

**R306 (22.11.2026, VPS-лаборатория):** реальный DTS Core стерео/5.1: при произвольной фрагментации сырого потока 11/97 байт GStreamer `dtsdec` терял часть PCM (даже с `exit=0`). После Matroska-демультиплексора полный PCM без потерь относительно эталона был побайтно одинаков при блоках 11/97/4096; `avdec_dca` и FFmpeg подтвердили длину. [R306](tools/test-real-dts-packet-boundaries-r306.py) PASS. **На LG 43NANO85A6A / R278 эта причина не подтверждена; не является утверждением о готовом исправлении.**

**R305 (22.11.2026, VPS-лаборатория):** настоящие события GstPad (`STREAM_START`, `FLUSH_START/STOP`, `EOS`) и смена caps проверены на экспериментальном R188 с GStreamer 1.24.2 и синтетическими данными: **8/8 PASS в обычной и ASan+UBSan сборках**. Системные пакеты и действующий LG не изменены. Это **не проверка декодирования реального DTS на webOS26** и не доказательство исправления первоначальной тишины. [Воспроизводимый R305](tools/run-r188-real-gstpad-events-r305.sh).

**R304 (22.11.2026):** новая самостоятельная C99-регрессия синтетических DTS-подобных кадров для R188: **ASan+UBSan 23/23 PASS, C99 -O2 23/23 PASS**, включая фрагменты, сбросы и контроль PTS. Это **не тест оригинального DTS-файла и не испытание R278 на кухонном LG**; обработчики GStreamer EOS/FLUSH/STREAM_START аппаратно не проверялись. [Тест R304](tools/run-r188-synthetic-firstframe-r304.sh).

**R303 (22.11.2026):** проверен [инструмент восстановления оригинальных данных R188](tools/recover-r188-original-pins-r303.py). Он принимает только совпадения с исходными SHA256; защищён от небезопасных путей в архивах и конфликтов с существующими файлами. Тесты PASS; архив VPS не содержит трёх искомых оригиналов (0/3). Декодер LG и установленный R278 не изменялись, исходный тест R188 пока недоступен.

**R302 — ограничение старой лаборатории (22.11.2026):** исходник экспериментального R186 умеет восстановить DTS-метаданные по частям заголовка, но не восстанавливает сам закодированный кадр; отдельный R188 в рабочем R278 на кухне не подтверждён. Повторный R188 ASan-тест на VPS заблокирован из-за трёх отсутствующих проверяемых файлов из `/tmp`, а не из-за сбоя DTS. [R302](tools/audit-r188-replay-prereqs-r302.py): 2/5 присутствуют с верными SHA256, 3 MISSING. Не переносить эту гипотезу в производственный DTS без полевых доказательств.

**R301 — анализ журнала завершения (22.11.2026):** новый [анализатор R301](tools/analyze-webos26-dts-lifecycle-r301.py) умеет сопоставлять EOS, переход в NULL и освобождение GStreamer. Из четырёх исторических `exit143` удалось подтвердить только наличие EOS/PCM; **строк LIFECYCLE в прежнем тесте не было**. 13 проверок и интеграционный тест на VPS PASS. Истинная причина первоначальной тишины на LG остаётся неподтверждённой.

**R300 (22.11.2026, офлайн):** диагностический R282 поддерживает необязательный отличающийся сигнал `USR1` при тайм-ауте. BusyBox на VPS возвращает 138 при его истечении, тогда как отдельный SIGTERM возвращает 143. Скрипты и регрессия PASS; **тип timeout на кухонном LG и причина исторического `143` неизвестны**, DTS-проигрывание не менялось.

**R299 — диагностика кода 143 (22.11.2026):** VPS-тест доказал, что BusyBox `timeout` при истечении лимита может вернуть **143** при уже напечатанном EOS; GNU `timeout` возвращает **124**. Исторические R282 `exit=143` поэтому не следует объявлять доказанным зависанием декодера. В R282 добавлены безопасные маркеры времени и завершения GStreamer; модель LG пока не проверялась новыми командами. [R299](tools/test-timeout-exit-r299.sh).

**R298 — уточнение тестов PCM/EOS (22.11.2026):** четыре исторических случая R282 дали DTS-декодер, EOS и ожидаемый PCM, но завершились `exit=143` (`SIGTERM`). До исправления вывод теста не отмечал это как неполное завершение. Исправленный R282 теперь требует `exit=0`; [R298](tools/test-webos26-r282-exit-r298.sh) проверен в изолированной среде: EOS+0 PASS, EOS+143 NOT PASS. Причина сигнала и первоначальной тишины **не установлена**; на производственном LG код не менялся.

**R297 — регрессионная проверка анализа результатов (22.11.2026):** R295 корректно отвергает `returnValue=false`, R296 проверен на реальных форматах R289/R294 (15 утверждений и CLI PASS), а новый [R297](tools/test-r295-r296-offline-r297.sh) успешно проверяет обработку поддельных ответов LS2. Исторический анализ AudioD/Starfish — 18/18 PASS. **Все эти тесты офлайн, не свидетельствуют о новом запуске DTS на LG.** В документации DTS Restore Plus описан схожий первый неудачный DTS-запуск после загрузки на других LG; совпадение механизма на кухне не доказано. Существующая установка не менялась.

**R294 — новая перезагрузка LG (22.11.2026):** по `/proc/uptime` установлена реальная новая загрузка кухонного телевизора (~04:27:24 UTC). После неё SHA256 плагинов/реестра, `umediaserver.env` и все четыре переменные живого `umediaserver` прошли проверку. В сессии без DTS: `codec=mpeg`, `ADEC1→MAIN`, ALSA PCM6 closed, активных PulseAudio-входов 0 и Starfish с DTS-плагинами не обнаружено. Это нормальный контрольный снимок, **не проверка первого DTS-воспроизведения после загрузки**. [R294](tools/capture-webos26-audio-session-r294.sh).

**R293 — клиенты PulseAudio:** `audiod` PID440 и `WebAppMgr` PID3217; прямого PulseAudio-клиента `starfish-media` PID20727 не обнаружено. Это указывает на **неподтверждённый промежуточный маршрут** между DTS и PCM-выходом. Следовательно, исправность DTS-декодирования подтверждена изолированно, реальный звук — владельцем; низкоуровневая цепочка не сертифицирована. [R293](tools/inspect-webos26-pulse-clients-r293.sh).

**R292 — уточнение источника PCM:** единственный активный PulseAudio sink-input принадлежит `WebAppMgr` PID3217, а DTS плагины загружены в `starfish-media` PID20727. Аппаратный ALSA-выход активен, но **не прослежена прямая цепочка DTS → PulseAudio → ALSA**; R286–R291 нельзя использовать как независимый тест содержимого DTS-PCM. Реальный звук подтверждён пользователем. [R292](tools/inspect-webos26-pulse-dts-r292.sh).

**Эталон аудиомаршрута R289–R291 (22.11.2026):** у работающего DTS на кухонном LG `codec=dts`, ALSA PCM6 RUNNING, `muted=false`, `volume=23`, выбран `tv_external_speaker`, маршрут `ADEC0→MAIN`. ARC `not_ready`, подключённых ARC-устройств нет, eARC mixer OnOff=0. Это показывает состояние при успешном воспроизведении; **не доказывает первопричину исторической тишины**. [Подробный отчёт](docs/WEBOS26_DTS_SILENCE_TRIAGE.md).

**R287, 22.11.2026 — повторная проверка 65 секунд:** 6/6 измерений `starfish-media` PID20727 и три DTS-модуля стабильны, `umediaserver`/`audiooutputd` активны, `codec=dts` 6/6. ALSA PCM6 `RUNNING` 6/6, аппаратный указатель увеличился на 3 121 152 кадра за 65 секунд (порядка 48 кГц); RSS процесса 118024→118032 КиБ (+8 КиБ), без смены PID. **Это проверка воспроизведения и буфера, не запись ненулевого аудиосигнала.** [R287 read-only](tools/monitor-webos26-dts-output-r287.sh).

**Аппаратный путь PCM (R286, 22.11.2026):** во время работающего DTS на кухне ALSA MARS PCM6 в состоянии RUNNING, формат S16_LE, 2 канала, 48000 Гц; `hw_ptr` увеличивается. Три замера R285 подтвердили стабильность процесса и RSS. Это проверка реального PCM-выхода, но не прямое измерение звука на динамиках. [Read-only диагностика R286](tools/check-webos26-audio-output-r286.sh).

**Повторное открытие фильма (22.11.2026):** DTS заработал сразу, без переключения на AC3 — проверено владельцем. Дополнительно удалённо через AlekS Core подтверждены активные umediaserver/audiooutputd, три DTS-библиотеки в новом starfish-media, codec=dts, контрольные суммы и переменные процесса. Причина первоначальной тишины не установлена; холодная загрузка ТВ и полная регрессия не проверены.

**История первого сбоя (22.11.2026):** три DTS-дорожки «Матрицы» изначально были без звука, переход AC3→DTS восстановил звук на всех трёх. Позднее полное закрытие и повторное открытие фильма дало звук DTS **сразу, без AC3**. Первоначальную тишину пока не удалось воспроизвести повторно; причина неизвестна.

**Первый отрицательный полевой тест (исторический, 22.11.2026):** DTS-дорожки были без звука до переключения на AC3. Этот результат сохранён как регрессионный случай, **не как текущее состояние**: в повторной сессии DTS звук заработал. Массовое распространение DTS для webOS 26 всё ещё не разрешено без холодного запуска и регрессии штатного плеера.

**Результат скрипта проверки окружения (22.11.2026):** установщик, SHA256 и фактические переменные `umediaserver` PASS; `RESULT=CONFIG_AND_PROCESS_ENV_PASS; NATIVE_AUDIO_NOT_YET_TESTED` означает только, что **сам скрипт не измеряет звук**. Позднее пользователь подтвердил DTS в Lampa, а R286/R287 подтвердили аппаратный PCM-буфер. Прослушивание в штатном LG Media Player отдельно **не проверено**, поэтому общественный релиз для webOS 26 преждевременен.

## Проверка DTS через Lampa на LG

Наш каталог приложений для Homebrew Channel: `https://gamefree24.ru/webos/repository.json`. На 22.11.2026 он отдаёт валидный JSON `packages`, содержит `lampa.tv` 2.3.0 и `mybylampa.tv` (lampa+) 2.3.0. Контрольный IPK lampa+ с внешнего источника соответствует SHA256 `0f6014790e6cb610cb1e53314b4f608483bcf8472589314ce86914c9126bb20c`.

Для webOS shell подготовлен [скрипт открытия штатного окна добавления репозитория](tools/open-aleks-repo-homebrew-channel.sh). Он запускает `org.webosbrew.hbchannel` через Luna `applicationManager/launch` с `launchMode=addRepository`. Пользователь должен нажать **Add repository** на экране и обновить каталог. Скрипт **не изменяет** настройки DTS и не устанавливает IPK.

Важно: тест DTS в Lampa не заменяет отдельного теста в штатном плеере LG. Доступность каталога и работа IPK зависят от сети телевизора и внешнего источника пакета.

## Порядок установки

1. Определить профиль и проверить загрузку всех компонентов; не отключать ABI-защиту.
2. Провести DTS 2.0, DTS 5.1 и AC3 в **изолированном** GStreamer.
3. Проверить текущее состояние `umediaserver.service`, пути `EnvironmentFiles`, `/var`, потенциальные чужие DTS-плагины, доступность recovery и отката.
4. Создать защищённую резервную копию исходной конфигурации. Применять изменения исключительно в `/var`/Homebrew, **не** в штатных системных библиотеках.
5. После установки подтвердить контрольные суммы и наличие способа отката; затем полностью перезагрузить.
6. Проверить DTS 2.0/5.1 в штатном плеере, обычные AC3/AAC, DVB, сторонние плееры и стабильность нескольких перезагрузок. При регрессии откатить.

**Не запускайте установщик webOS26-кандидата на других LG:** он сознательно проверяет конкретный медиа-ABI/версию GStreamer, раздел eMMC `/dev/mmcblk0p59` и владельца медиаслужбы. Этот механизм необходим для первого полевого теста и должен стать адаптивным только после проверок на других моделях.

Для совместимых старых ARMv7/GStreamer 1.16 предусмотрен [install-universal.sh](install-universal.sh), сначала запускайте `verify`. Для webOS26 до подтверждения штатного медиаплеера используется только профиль кухни, документация в [README.md](README.md).

**Статус:** поддержка других моделей расширяется по мере проверенных аппаратных тестов. Универсальной гарантии работы на всех LG нет.
